## 0. 文档定位与阅读指引

### 原型实现状态及口径修正

以下修正优先于后文的早期设计假设；本文并非全部功能已实现的声明。

- **2026-11-03 决策变更：界面改为纯 C + Win32（GDI 自绘），不使用 MFC。** 本机仅有 MinGW-w64 工具链，没有 Visual Studio / Windows SDK / MFC，纯 C 方案是唯一能在本机编译、运行并截图验证的路线。第 2.1 节保留原选型分析作为历史记录，其 MFC 结论已被该变更取代。采集与存储核心仍为 C++17，通过 `ui/bridge.h` 的 C ABI 与 C UI 连接。
- UI 实现位于 `ui/`（主窗口、主题、格式化、绘制、托盘），视觉规范位于 `design-system-signal-paper/`。构建命令：`bash build.sh`（核心与存储测试，需先生成 `build/sqlite3.o`）后执行 `bash build_ui.sh`，产出 `build/trafficmon_ui.exe`。
- UI 冒烟测试：`python tests/ui_smoke.py`（需管理员权限以覆盖 ETW 归属；测试会以 `--exit-after` 运行 UI 并断言 python.exe 精确 1020/1020 字节、会话 `etw`/`closed=1`、schema v3，并以 `--no-etw` 断言无应用字节）。
- UI 已验证项：仪表盘、历史日视图、历史分页与空状态的截图检查（Windows 11 10.0.28000）；轻量模式的截图检查（网卡速度、所选程序行随负载更新）；四款主题（纸白、墨夜、海雾、琥珀）下主窗口与轻量模式的截图检查；程序归属由 `tests/ui_smoke.py` 与数据库核对。
- UI 未验证项：150%/200% DPI、真实非管理员降级体验（轻量模式程序列显示“—”）、托盘菜单切换轻量模式与主题的交互点击、轻量模式中“流量监控”选择程序的交互、托盘在 Explorer 重启后的恢复、睡眠恢复、跨 Windows 版本兼容性、多显示器与任务栏位于左侧/顶部时的右下角定位。
- 运行测试前需确认没有残留的 ETW 会话（`logman query -ets` 中的 `TrafficMon-*`）。被强制结束（`taskkill /F`）的进程不会调用 `tm_stop()`，其会话会残留并导致后续 ETW 无法归属应用字节；可用 `logman stop <名称> -ets` 清理。

- 连接表不提供收发字节计数，不能用于估算应用流量。降级模式仅显示 TCP 连接、UDP 本地端点和 PID，应用字节数为 N/A；UDP 连接表不提供远端地址。网卡计数继续可用。
- 当前 M2 原型将网卡与应用小时统计分别写入 `nic_hourly` 和 `application_hourly`，禁止相加。应用记录保存局域网/互联网拆分；网卡计数无此拆分，对应列为 NULL（未分类），不等于 0。
- 小时桶以 UTC 存储，同时写入该小时对应的本地日历标签；`--day YYYY-MM-DD`、`--month YYYY-MM` 按本地自然日/月查询，跨夏令时的日界线由日历标签保证，不依赖固定时区偏移；跨越本地午夜的 UTC 小时桶按桶开始时刻归属到某一天（半小时/四十五分钟时区存在最多 1 小时的归属误差）。迁移前的 v1/v2 行按迁移时的时区近似回填标签。
- schema v3 增加本地日与 LAN 拆分列，并在金额列上保留 `typeof(...)='integer'` 约束，防止 SQLite 整数溢出静默转为浮点造成静默损坏；v1/v2 数据库自动迁移。
- schema v2 增加 `collection_session`：记录启动时间、最后成功提交时间、ETW/连接表模式以及正常结束状态。打开或未正常结束不等于已确认崩溃，模式记录不证明 ETW 无丢包；v1 历史数据不补造覆盖信息。
- 每 60 个采样周期事务提交，正常退出在停止 ETW 并 Drain 尾部事件后再次提交。崩溃或写入失败可能丢失未提交数据，不承诺零丢失。
- 进程身份的解析顺序：启动时快照现存进程；运行中订阅 Kernel-Process 的 ProcessStart（无镜像字段，仅能尝试实时查询）、ImageLoad（首条镜像即主程序，携带完整 NT 路径，经卷映射转为盘符路径）、ProcessStop（携带可执行文件 basename）。ETW 实时送达延迟实测约 1.5～2.7 秒，短于该延迟的进程在事件到达时已退出，其流量先在内存挂起，待 ProcessStop 校验 basename 后归属；仍无法解析的（事件丢失、启用订阅前已启动且已退出等）以 `unknown:<会话>:<PID>` 保存并在停止时提交，不借用随后复用该 PID 的进程名称。PID 0/4 记为 `System`。ImageLoad 的字段偏移仅在本机 Windows 11 (10.0.28000) 实测，跨版本兼容性未验证；启用 IMAGE 关键字会显著增加事件量。
- ETW 丢事件诊断、睡眠恢复后的会话重建仍未完善；`collection_session` 只记录模式与提交时间，不证明 ETW 无丢包。
- `bash build.sh` 构建并运行模块测试；`python tests/integration_test.py` 验证本地采集落盘、重启累计、本地日/月查询、短命进程身份归属及 ETW 尾部提交。真正的非管理员权限、睡眠恢复和跨 Windows 版本兼容性尚未完成实测。


本方案面向产品经理、客户端开发工程师、测试工程师、运维/发布负责人，用于立项评审与首版开发排期。内容分三部分：

1. 需求梳理与边界定义（第 1 章）
2. 架构与实现设计（第 2～6 章）
3. 交付与路线图（第 7～9 章）

## 1. 需求梳理与边界定义

### 1.1 目标 Windows 版本与环境假设

- 目标系统：Windows 10 1809+ 、Windows 11（x64 为主，不单独适配 ARM64/x86 32 位，如需支持另行评估）。
- 网络场景：以太网、Wi-Fi、常见 VPN 虚拟网卡（TAP/TUN、WireGuard、企业 VPN 客户端创建的虚拟适配器）、多网卡同时在线。
- 不假设用户环境已安装 WinPcap/Npcap 等第三方驱动；如后续方案涉及驱动，须在安装程序中自带并明确提示。

### 1.3 采集方式路线：分阶段

进程级流量归属是本方案风险最高、精度与权限成本权衡最大的部分，采用**分阶段路线**：

- **阶段 A（v1.0，纯用户态，无需驱动）**
  - 原理：周期性（建议 1～2 秒）调用 `GetExtendedTcpTable` / `GetExtendedUdpTable`（IP Helper API）获取当前系统所有 TCP/UDP 连接的四元组（本地地址:端口、远端地址:端口）及其 `dwOwningPid`，建立"连接 → 进程"的映射表。
  - 流量数据来源：结合 `GetIfTable2` / `GetIfEntry2` 拿到网卡级别的总字节数（可靠、系统提供），再通过 ETW（Event Tracing for Windows）的 **Microsoft-Windows-Kernel-Network** provider 订阅 TCP/UDP 收发事件（事件 ID 10/11 为 IPv4 TCP 发送/接收，26/27 为 IPv6 TCP，42/43、58/59 为 UDP；M1 原型已实测可用），该事件带有 `pid`，可直接获得逐进程、逐连接的字节数增量，精度明显优于"轮询连接表再估算"。
  - 限制（必须在方案与产品文档中向用户说明）：
    - 极短生命周期的连接（建立后几十毫秒内关闭）可能在两次轮询之间被错过归属，但 ETW 事件路径本身是事件驱动而非轮询，这类问题主要出现在"连接表轮询"兜底路径，不是 ETW 主路径的问题；两者组合使用可把误差控制在可接受范围。
    - 原始 socket、某些内核组件（如系统进程、驱动产生的流量）可能无法关联到具体用户进程，需归入"系统/未知进程"类别。
    - 该方式**不需要管理员权限读取 TCP 表本身**，但订阅 ETW 内核 provider **需要管理员权限**（ETW 会话创建权限要求），因此首版仍需以管理员身份运行或申请提权，详见 6.3。
  - 结论：阶段 A 已能满足首版"按应用统计上传/下载流量"的验收标准，且不引入驱动签名、WFP 安装等高风险项，适合首版快速上线。

- **阶段 B（v1.1 之后，引入 WFP 轻量过滤驱动，可选）**
  - 原理：使用 Windows Filtering Platform（WFP）的 Callout 驱动在网络层对每个数据包打标（经 `FwpmConnectionGetById` 等关联到进程），实现更精确、更低延迟的逐包归属，尤其能覆盖阶段 A 的"极短连接"盲区，并为后续"限速""防火墙拦截"打基础。
  - 代价：需要开发并数字签名内核驱动（WHQL 或至少需要 EV 代码签名证书 + 测试签名流程）、安装时需要管理员权限加载驱动、增加了驱动兼容性测试矩阵（不同 Windows 版本、安全软件冲突）。
  - 决策建议：先用阶段 A 验证产品市场匹配度和核心体验，阶段 B 作为精度与高级功能（限速/拦截）的技术储备，不阻塞首版交付。

### 1.4 验收标准与假设（关键功能项）

| 功能 | 验收标准 | 假设 |
|---|---|---|
| 实时速度显示 | 托盘图标/主窗口 1 秒内刷新一次，误差与系统任务管理器"性能"页网速相差 <5% | 采集周期 1 秒 |
| 按网卡查看 | 多网卡环境下，每张网卡独立显示实时速度与当日/当月累计 | 虚拟网卡（VPN）视为独立网卡项，可被筛选/隐藏 |
| 按应用统计 | 任意时刻可查看 Top N 进程的上传/下载累计，日/月粒度查询响应 <1 秒（本机数据量 ≤ 1 年） | 进程以"可执行文件完整路径 + 签名/描述"作为身份标识，进程重启后沿用同一统计条目 |
| 月度流量上限提醒 | 用户设置阈值后，累计流量达到阈值的 80%/100% 时弹出系统通知 | 月度周期以自然月计算，可在设置中选择"账单日"起始 |
| 应用流量阈值 | 单应用日/月流量超过用户设定值时通知 | 阈值单位 MB/GB，支持按应用单独设置 |
| 新应用首次联网提示 | 本机历史记录中从未出现过的可执行文件首次产生网络流量时，气泡通知 | 以"进程全路径的首次出现时间"判断，重装/路径变化会被视为新应用（已在文档中注明） |
| 应用流量突增提示 | 当某应用当日流量超过其过去 7 天日均值的 N 倍（默认 3 倍，可配置）时提示 | 需要至少 3 天历史数据才启用突增检测，避免冷启动误报 |
| CSV 导出 | 按当前筛选条件导出流量明细，字段含时间、网卡、进程、上传、下载、方向（局域网/互联网） | 单次导出行数超过 10 万行时分批写出，避免 UI 卡顿 |
| 数据保留与清空 | 用户可设置保留期限（7/30/90/365 天/永久），到期自动清理；提供"立即清空全部记录"按钮并二次确认 | 清空操作不可逆，需明确二次确认文案 |

## 2. 架构与实现设计

### 2.1 技术选型：MFC vs Delphi

> **状态（2026-11-03）：以下 MFC 推荐已被决策变更取代，界面改为纯 C + Win32，见第 0 节。** 下表保留为选型分析的历史记录；采集、存储与 ETW 相关结论仍然有效。

| 维度 | MFC（C++） | Delphi（Object Pascal） |
|---|---|---|
| 系统级 API 可用性（IP Helper、ETW、WFP、Winsock） | 原生支持，官方 SDK 示例齐全，WFP/ETW 的头文件与文档均为 C/C++ 优先 | 需要第三方绑定或自行声明 API，ETW/WFP 的 Delphi 生态资料少 |
| 未来扩展到驱动开发（阶段 B WFP 驱动） | 驱动本身必须用 C/C++（WDK 要求），MFC 应用层与驱动同语言，IPC/联调成本低 | 驱动仍需 C/C++ 编写，应用层与驱动层语言不一致，增加团队技能面要求 |
| UI 开发效率 | 相对繁琐，托盘/悬浮窗/图表需要手写或引入第三方库（如 ChartDirector、自绘） | VCL 组件生态成熟，TTrayIcon、图表组件（TeeChart）开箱即用，UI 开发效率更高 |
| 本地存储 | 需自行集成 SQLite（成熟方案，如 sqlite3.c 直接编译） | 同样可集成 SQLite，FireDAC 对 SQLite 支持也较好 |
| 团队技能与招聘 | C++/MFC 工程师供给相对充足，尤其在系统工具类厂商 | Delphi 工程师存量在收缩，招聘与长期维护风险较高 |
| 长期可维护性 | 社区活跃度、工具链（VS、WDK、调试器）更新频繁 | Embarcadero 生态更新节奏较慢，版本授权成本 |

**推荐结论：MFC（C++）。**

理由：本方案的核心技术难点（IP Helper 轮询、ETW 内核事件订阅、后续 WFP 驱动）全部是系统级 C/C++ API，MFC 与这些能力同语言、同工具链（Visual Studio + WDK），减少跨语言绑定的维护成本和联调风险；且阶段 B 一旦启动驱动开发，应用层必须能直接复用驱动团队的结构体定义和 IPC 协议，MFC 路线的工程摩擦明显更小。Delphi 在 UI 开发效率上有优势，但本产品 UI 复杂度中等（托盘+主窗口+设置+图表），MFC 配合现成图表库（如开源 Chart Control 或自绘 GDI+）可以满足，不构成决定性短板。

后续章节原基于 **MFC + C++17 + Visual Studio 2022 + WDK（阶段 B 预留）** 展开；2026-11-03 起界面层改为纯 C + Win32，采集/存储层仍为 C++17 + WDK（阶段 B 预留）。

### 2.2 总体架构分层

```
┌─────────────────────────────────────────────────────────┐
│  UI 层（纯 C + Win32，见 2.3）                              │
│  主窗口 / 托盘 / 悬浮窗（后续）/ 设置窗口 / 通知气泡        │
├─────────────────────────────────────────────────────────┤
│  查询/图表层（Query Service）                              │
│  按日/周/月聚合查询、筛选（网卡/应用/方向/局域网互联网）     │
├─────────────────────────────────────────────────────────┤
│  规则引擎层（Rule Engine）                                 │
│  阈值提醒、新应用检测、流量突增检测                          │
├─────────────────────────────────────────────────────────┤
│  聚合层（Aggregator）                                      │
│  内存中按秒累计 → 按分钟/小时 flush 到存储                  │
├─────────────────────────────────────────────────────────┤
│  存储层（Storage，SQLite）                                 │
│  网卡流量表 / 进程流量表 / 进程身份表 / 配置表 / 规则表      │
├─────────────────────────────────────────────────────────┤
│  采集层（Collector）                                       │
│  网卡级：GetIfTable2 轮询                                  │
│  进程级：ETW Kernel-Network Provider 订阅 + IP Helper 连接表兜底      │
├─────────────────────────────────────────────────────────┤
│  系统恢复层（Resilience）                                   │
│  断网/睡眠唤醒/网卡切换事件监听 → 采集会话重建                │
└─────────────────────────────────────────────────────────┘
```

模块边界原则：采集层只产出"原始事件流"（时间戳、网卡 ID/进程 ID、方向、字节数），不做任何业务判断；聚合层负责时间粒度归并；规则引擎和查询层都只读聚合层写入存储层的数据，不反向依赖采集层。

### 2.3 核心模块清单

| 模块 | 职责 | 关键类/组件 |
|---|---|---|
| `NicCollector` | 周期轮询网卡级字节计数 | 封装 `GetIfTable2`/`GetIfEntry2` |

## 3. 数据模型与本地存储

### 3.1 存储选型

使用 **SQLite**（嵌入式、单文件、零部署依赖），通过官方 amalgamation 源码直接编译进程序，不引入外部运行库依赖。

### 3.2 表结构

```sql
-- 网卡字典表
CREATE TABLE nic (
    nic_index     INTEGER PRIMARY KEY,
    nic_name      TEXT NOT NULL,
    nic_type      TEXT,            -- ethernet / wifi / vpn / other
    is_hidden     INTEGER DEFAULT 0
);

-- 进程身份表
CREATE TABLE process_identity (
    process_key_id INTEGER PRIMARY KEY AUTOINCREMENT,
    exe_path        TEXT NOT NULL,
    display_name    TEXT,
    publisher       TEXT,
    first_seen_ms   INTEGER NOT NULL,
    UNIQUE(exe_path)
);

-- 小时粒度流量聚合表（主存储粒度）
CREATE TABLE traffic_hourly (
    hour_bucket     INTEGER NOT NULL,   -- unix 小时桶
    nic_index       INTEGER NOT NULL,
    process_key_id  INTEGER NOT NULL,   -- 0 = 该网卡不区分进程的总量
    bytes_up_lan    INTEGER DEFAULT 0,
    bytes_down_lan  INTEGER DEFAULT 0,
    bytes_up_wan    INTEGER DEFAULT 0,
    bytes_down_wan  INTEGER DEFAULT 0,
    PRIMARY KEY (hour_bucket, nic_index, process_key_id)
);

-- 日粒度聚合表（按日/周/月查询的加速表，由小时表定时汇总生成）
CREATE TABLE traffic_daily (
    day_bucket      INTEGER NOT NULL,   -- unix 日桶（本地时区）
    nic_index       INTEGER NOT NULL,
    process_key_id  INTEGER NOT NULL,
    bytes_up_lan    INTEGER DEFAULT 0,
    bytes_down_lan  INTEGER DEFAULT 0,
    bytes_up_wan    INTEGER DEFAULT 0,
    bytes_down_wan  INTEGER DEFAULT 0,
    PRIMARY KEY (day_bucket, nic_index, process_key_id)
);

-- 用户配置表
CREATE TABLE app_setting (
    key   TEXT PRIMARY KEY,
    value TEXT
);

-- 阈值规则表
CREATE TABLE threshold_rule (
    rule_id        INTEGER PRIMARY KEY AUTOINCREMENT,
    rule_type      TEXT NOT NULL,   -- monthly_total / app_daily / app_monthly
    process_key_id INTEGER,         -- NULL 表示全局（月度总量）
    limit_bytes    INTEGER NOT NULL,
    notify_at_pct  TEXT DEFAULT '80,100'
);
```

设计要点：
- **周查询**直接由 `traffic_daily` 按 `day_bucket` 范围聚合即可得出，不需要新表，验证了 1.2 节"周视图延后不影响数据模型"的判断。
- **局域网/互联网区分**在采集层写入事件时即标记 `isLan`（依据目标 IP 是否属于 RFC1918 私有地址段 / 链路本地地址），聚合时分别累加到 `*_lan` / `*_wan` 字段，查询层可按方向筛选或合并显示。
- 小时表保留原始聚合粒度用于"今日/本周内的小时级图表"；日表用于长周期查询加速，避免跨月查询时扫描大量小时行。
- 保留期限清理：定时任务按 `app_setting` 中配置的保留天数，删除 `hour_bucket`/`day_bucket` 超出范围的行（日表通常保留更久，小时表可配置更短的保留期以控制数据库体积）。

### 3.3 系统流量与应用流量的统计差异说明（必须在产品中呈现）

- 网卡总流量（`nic_index` 对应、`process_key_id = 0` 的行）来自 `GetIfTable2`，是操作系统网卡驱动层面的计数，包含所有进程、系统服务、广播/组播、协议头开销等。
- 应用流量（按 `process_key_id` 归属的行）来自 ETW 事件 + 连接表关联，统计的是"应用层可观测到的 socket 收发字节"，不含部分协议头开销，也无法覆盖无法关联到进程的流量（如内核组件、原始 socket）。
- 因此 **"各应用流量之和"通常会小于"网卡总流量"**，差值部分会在 UI 上以"系统/未知"分类呈现，并在帮助文档和首次使用引导中说明原因，避免用户误以为是统计错误。

## 4. 恢复机制：断网 / 睡眠唤醒 / 网络切换

| 场景 | 检测方式 | 恢复动作 |
|---|---|---|
| 网络中断 | `NotifyIpInterfaceChange` 回调 + 网卡轮询读数失败/归零 | 标记该网卡为"离线"，停止累计异常跳变；恢复时以新读数为基线重新开始差值计算，避免断网期间的计数器重置被误判为"瞬时大流量" |
| 系统睡眠/唤醒 | 监听 `WM_POWERBROADCAST`（`PBT_APMSUSPEND` / `PBT_APMRESUMEAUTOMATIC`） | 睡眠前记录各网卡/ETW 会话的最后读数并 flush 到存储；唤醒后重建 ETW 会话（原会话在睡眠期间可能失效）、重新基线化网卡计数器 |
| 网络切换（如 Wi-Fi 切换、VPN 连接/断开） | `NotifyIpInterfaceChange` 回调识别网卡增删/状态变化 | 新网卡自动加入 `nic` 字典表并开始采集；移除的网卡标记为非活跃但保留历史数据；VPN 虚拟网卡视为独立网卡项 |
| 应用崩溃重启后的统计连续性 | 启动时从存储层读取各网卡最后一次持久化的计数器基线 | 避免程序重启导致的计数器基线丢失引发的"虚假流量跳变" |

通用原则：**所有基于计数器差值的统计，都要对"本次读数 < 上次读数"（计数器被重置，如网卡重新初始化）做保护**，此时按"本次读数"作为新增量，不做差值相减，避免出现负数或异常大的流量记录。

## 6. 非功能设计

### 6.1 性能与资源占用

- 采集频率：网卡级 1 秒轮询（开销极低，`GetIfTable2` 单次调用成本可忽略）；ETW 事件为系统推送，不消耗额外 CPU 轮询开销，主要成本在事件解析，需确保解析逻辑高效（避免每个事件做日志 IO）。
- 聚合写盘频率：内存聚合 60 秒 flush 一次，减少 SQLite 写入频率；使用单一后台线程做写入，避免 UI 线程阻塞。
- 验收目标：常驻后台 CPU 占用 < 1%（空闲时），内存占用 < 50MB（不含系统进程自身开销），对实际网速无感知影响（采集不经过数据路径，只读取计数器/事件，不转发或拦截数据包，因此阶段 A 方案不会对网速产生影响；阶段 B 引入 WFP callout 后需专项测量延迟增量）。

### 6.2 兼容性测试矩阵

| 维度 | 覆盖项 |
|---|---|
| 系统版本 | Windows 10 1809/21H2、Windows 11 22H2/23H2+ |
| 网卡类型 | 有线以太网、Wi-Fi、USB 网卡、蓝牙网络共享（可选） |
| VPN/虚拟网卡 | WireGuard、OpenVPN TAP、企业 VPN 客户端（如 Cisco AnyConnect 类虚拟适配器） |
| 多网卡组合 | 双网卡同时在线、禁用/启用网卡切换、网卡优先级变化 |
| 电源场景 | 睡眠/唤醒、混合睡眠、合盖/开盖（笔记本） |
| 权限场景 | 管理员运行、非管理员运行（验证降级提示） |
| 安全软件共存 | 主流杀毒/安全软件环境下的安装与运行（验证无误报、无冲突） |

### 6.3 权限模型与回退行为

- **阶段 A（首版）**：
  - 读取 `GetExtendedTcpTable`/`GetIfTable2` 不需要管理员权限。
  - 订阅 ETW `Microsoft-Windows-Kernel-Network` provider **需要管理员权限**（创建实时 ETW 会话的系统要求）。
  - 回退行为：若程序未以管理员权限启动，**网卡级总流量监控仍正常工作**，但**按应用的流量归属功能降级**——此时改用 IP Helper 连接表轮询做近似估算（精度较低，尤其对短连接不敏感），并在 UI 上明确标注"当前为非管理员模式，应用级统计为估算值，建议以管理员身份运行以获得精确统计"。
  - 安装程序通过 manifest 请求 `requireAdministrator` 或提供"以管理员身份运行"快捷方式选项，不强制每次都 UAC 提权（避免开机启动时弹 UAC 打扰用户），而是在首次安装时引导用户选择"始终以管理员身份运行"的计划任务方式启动，以兼顾开机自启和权限需求。
- **阶段 B（后续，WFP 驱动）**：
  - 驱动安装/加载需要管理员权限，且驱动签名需满足 Windows 代码完整性要求（测试机需开启测试签名模式，正式发布需 EV 证书 + 必要时提交 WHQL）。
  - 回退行为：驱动加载失败（签名问题、安全软件拦截、系统策略限制）时，自动降级回阶段 A 的用户态方案，并提示用户驱动未能加载的原因及影响范围。

### 6.4 安装、卸载与升级

- 安装程序（建议 Inno Setup 或 WiX）职责：
  - 释放主程序、SQLite 运行所需文件（无需额外运行库，静态编译 SQLite）。
  - 写入开机启动项（建议使用计划任务而非注册表 Run 项，便于控制"以管理员权限启动"且避免被部分安全软件标记为"注册表启动项"风险项）。
  - 首次安装时弹出权限说明页（见 6.3），用户确认后再继续。
- 卸载：
  - 默认保留用户数据（流量历史、设置），卸载向导提供"同时删除本机数据"的勾选项，默认不勾选，避免误删。
- 升级：
  - 增量升级通过版本号检测 + 数据库 schema 迁移脚本（`PRAGMA user_version` 控制迁移步骤），避免跨版本升级时历史数据丢失或崩溃。
  - 升级前自动备份数据库文件（一份 `.bak`），迁移失败时回滚。

### 6.5 隐私与数据边界

- 所有流量统计数据默认仅保存在本机 SQLite 文件中，不上传任何服务器，产品说明中明确声明。
- 用户可控项：数据保留期限、清空全部记录、隐藏指定网卡/应用的统计（隐藏不等于不采集，需在设置中明确区分"停止监控"与"界面隐藏"两种语义，避免用户误解）。
- 进程身份表记录的是"可执行文件路径/描述/签名信息"，不采集窗口标题、剪贴板、文件内容等无关隐私数据，方案边界需在隐私说明文档中列出，避免误解为深度监控工具。

## 7. 模块接口与关键流程（补充说明）

### 7.1 启动流程

1. 读取配置（权限状态、保留期限、阈值规则）。
2. 初始化 `StorageManager`，执行必要的 schema 迁移。
3. 启动 `NicCollector`（无权限要求，始终可用）。
4. 检测当前进程权限：若为管理员，启动 `ProcNetCollector` 的 ETW 订阅路径；否则启动降级的连接表轮询路径，并在 UI 标注降级状态。
5. 启动 `TrafficAggregator` 定时 flush 任务、`RuleEngine` 定时扫描任务。
6. 创建托盘图标，主窗口默认最小化或按用户上次状态恢复。

### 7.2 查询流程（示例：查看某应用本月流量）

1. UI 层传入筛选条件（`process_key_id`、月份范围、方向筛选）。
2. `QueryService` 组装 SQL，优先查 `traffic_daily`（按天聚合后在内存里按月求和），而不是逐小时查询，保证大范围查询的响应速度。
3. 返回结果供图表层渲染（按日折线）及汇总卡片（本月累计值）展示。

| M5 | 恢复机制 + 安装卸载升级 + 兼容性测试 | 候选发布版本 |
| M6 | 测试矩阵跑通 + 文档（权限说明、隐私说明、统计差异说明） | 正式发布 |

### 9.2 风险清单

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 非管理员运行下应用级统计精度不足 | 用户体验/信任度下降 | UI 明确标注估算模式；引导用户以管理员方式运行；长期靠阶段 B 驱动方案改善 |
| ETW 会话在部分安全软件/组策略环境下被限制 | 进程级统计功能不可用 | 检测订阅失败并自动降级到连接表轮询；记录诊断日志辅助排障 |
| 短生命周期连接归属不准 | 部分应用流量被归为"系统/未知" | 文档中说明统计差异来源；阶段 B 用 WFP 驱动改善 |
| SQLite 文件在长期运行后体积过大 | 查询变慢、磁盘占用增加 | 保留期限自动清理 + 日粒度表加速长周期查询 + 定期 `VACUUM` |
| 安装包携带的开机启动方式被安全软件误报 | 安装/首次使用体验受损 | 优先使用计划任务而非注册表 Run 项；代码签名；向主流安全软件厂商提交白名单申请 |
| 后续 WFP 驱动开发周期与签名流程不可控 | v2.0 限速/拦截功能延期 | 阶段 B 作为独立里程碑单独评估排期，不绑定首版发布节奏 |
| 多网卡/VPN 环境下网卡 ID 复用或变化 | 历史数据与当前网卡对应错乱 | `nic` 字典表以网卡 GUID（而非易变的 ifIndex）作为稳定关联键，ifIndex 仅作运行时缓存 |

## 10. 后续版本展望（仅列方向，不在本方案详细设计）

- **限速**：需 WFP callout 驱动做流量整形（QoS），涉及内核态数据路径修改，稳定性风险高，需独立的驱动测试体系。
- **防火墙拦截**：需 WFP callout 驱动做包过滤决策，涉及系统级网络拦截，需格外谨慎的白名单/误拦截处理机制，且与安全软件冲突概率高。
- **局域网设备监控**：需 ARP 扫描或端口镜像/旁路抓包能力，涉及对非本机设备的信息采集，存在法律与隐私边界问题，需先完成合规评估。
- **抓包与协议分析**：需 Npcap/WinDivert 级别的驱动能力，交付与维护成本显著高于本方案阶段 A/B，建议作为独立产品线评估，而非在本产品内叠加。

以上四项均明确列为 v2.0 及以后，首版不实现，仅在架构设计中保留"采集层可替换/可扩展"的接口边界（见 2.2 模块边界原则），以降低后续演进成本。
